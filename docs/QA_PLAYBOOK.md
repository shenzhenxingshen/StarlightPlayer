# QA 执行手册

> 最后核对：2026-10-16。本文把 [设备与发布候选测试矩阵](DEVICE_TEST_MATRIX.md) 中的 P（播放）、S（同步）、L（生命周期/系统）、U（布局/可用性）用例展开为可执行步骤。每次发布候选复制 [`test-runs/TEMPLATE.md`](test-runs/TEMPLATE.md) 留下结果；没有匹配制品、设备和证据的项目一律不算 PASS。

## 1. 使用原则

### 1.1 状态

| 状态    | 使用条件                                                     |
| ------- | ------------------------------------------------------------ |
| PASS    | 全部步骤满足预期，记录了指定 build、设备、日期、测试者和证据 |
| PARTIAL | 只执行部分步骤，或证据不足以覆盖整个用例                     |
| FAIL    | 可复现地不满足预期，已记录实际表现、复现步骤和问题编号       |
| BLOCKED | 因设备、账号、二进制或外部条件无法执行；必须写明阻塞原因     |
| NOT RUN | 尚未执行；不能用另一个设备、旧 build 或自动化结果代替        |

如果同一 ID 包含多个参数或设备，只要必需组合未完成，就不能把整个 ID 标为 PASS；可以拆为子记录，例如 `P03-iOS-N1`、`P03-Android-N7`。

### 1.2 候选制品前置

每轮开始前完成并记录：

1. 冻结 Git commit；确认工作区和候选构建对应，不在测试中途换包。
2. 记录营销版本、构建号、安装来源以及 APK/AAB/Archive/TestFlight 制品 SHA-256。
3. 最终结论使用 release/商店候选；Debug 只可做预检，不能替代正式签名包。
4. 记录设备品牌/型号、系统版本/API、屏幕/窗口尺寸、方向、时区、自动时间、电池策略、字体和辅助技术状态。
5. 指明是全新安装、保留数据重装，还是从 0.6.0/0.7.0/其他版本升级。
6. 确认 App 显示的版本与实际安装包一致，21 首曲目可见；开始前导出一份诊断或清楚记录日志基线。
7. iOS 13/14 只有在候选 Archive 的 `MinimumOSVersion` 允许安装后才执行；否则标记为 BLOCKED/NOT RUN，并在版本测试记录中说明。现有 build 的兼容事实见 [版本发布记录](release-records/README.md) 和 [当前风险](KNOWN_ISSUES.md)。

### 1.3 通用测试数据和观察项

- P 组默认使用普通模式、关闭同步，避免墙钟对齐影响核心模式判断；S 组单独开启同步。
- 需要快速自然结束时优先选较短的 A04；A05 专项必须使用 A05。两首的业务标准时长、解码时长和编码事实以 [音频资产台账](AUDIO_ASSETS.md) 为准。不得 seek 到尾部代替自然完成，因为主动 seek 会改变当前遍计数资格。
- 每次换曲/换遍同时观察：声音、曲目标题、播放状态、进度、当前遍数、每首重复遍数、统计数据和诊断日志。
- “完整一遍”是从 0～1.5 秒内取得资格并自然到达有效曲尾；只播放尾段不应计数。
- 需要验证跨重启时，先记录退出前曲目、位置、当前遍数、模式、同步状态和用户播放意图，再记录重开后的对应值。
- 除明确要求新任务/全新安装的步骤外，不清数据、不重选歌曲，以免掩盖持久化问题。

### 1.4 最低证据

每个用例至少保留：开始/结束时间、实际结果、执行记录中的状态，以及能证明关键断言的截图、录屏、诊断日志或系统日志。播放边界用例优先录屏并同时导出 App 诊断；长时用例记录开始、中间、结束三个节点。

外部证据以 `EV-<用例>-<序号>` 编号，原文件放受控存储；仓库记录链接、SHA-256、采集时间和脱敏状态。不得向公开仓库提交用户诊断、系统 bugreport、`.xcresult`、完整 logcat 或含账号/设备标识的录屏。详见 [`test-runs/README.md`](test-runs/README.md)。

## 2. P：播放、模式和计数

### P01 单曲播放，N=1

- **前置：** 普通模式、同步关闭；选择 A04 形成新任务；模式切到“单曲播放”；重复遍数为 1。此时已完成累计和模式 session 都是 0；按显示规则，播放页不显示当前遍数或每首重复遍数，不能把隐藏值写成“当前遍数为 0”。
- **步骤：** 从开头播放并自然结束；确认停止后再次按播放。
- **期望：** 第一遍只计 1 次并停止，不自动重播；再次播放被视为新任务，已完成累计和模式 session 先清零，再从第 1 遍重新开始，旧任务不能继续累加为 2。N=1 且为单曲播放时，两项遍数仍按规则隐藏，内部清零应通过日志/持久化状态和后续行为验证。
- **证据：** 结束前后和再次播放后的录屏；诊断中的 QueueEnded、mode/session/repeat 和停止动作。

### P02 单曲播放，N=7

- **前置：** 与 P01 相同，但重复遍数设为 7。
- **步骤：** 不 seek、不重选曲目，让 A04 自然完成 7 遍；逐遍记下结束时间和计数。
- **期望：** 第 1～6 遍结束后继续当前曲，第 7 遍结束后才停止；每个有效周期只增加 1，不漏计/重计。
- **证据：** 7 个 QueueEnded/计数节点、最终停止画面和诊断文件。

### P03 单曲循环，N=1/7

- **前置：** 普通模式、同步关闭、模式为“单曲循环”；分别建立 N=1 和 N=7 的独立新任务。
- **步骤：** N=1 至少完成 3 遍；N=7 至少完成 8 遍，观察第 7→8 遍边界。
- **期望：** 达到每组 N 后仍播放同一首；用于模式决策的 session 在边界正确归零，用户可见累计遍数连续增长，不因继续循环变回 0。
- **证据：** N=1 的 3 个边界、N=7 的第 6/7/8 遍录屏与 QueueEnded 日志。

### P04 列表播放，N=2

- **前置：** 选择非最后一首形成新任务；同步关闭；模式为“列表播放”；N=2。
- **步骤：** 自然播放当前曲两遍并进入下一首；让下一首也完成两遍；另从列表最后一首建立新任务并完成两遍。
- **期望：** 每首第 1 遍结束不换曲，第 2 遍结束才换下一首；自动换曲后，新曲的已完成累计和模式 session 都清零。新曲从 0～1.5 秒取得当前周期资格后，用户可见“当前遍数”应为 1，而不是把内部已完成累计 0 直接显示为 0；最后一首第 2 遍后停止。
- **证据：** 两首各两个结束节点、自动换曲瞬间、最后一首停止和曲目/计数日志。

### P05 列表循环，N=2

- **前置：** 同步关闭；模式为“列表循环”；N=2；先选择倒数第二首以缩短到列表回绕的路径。
- **步骤：** 倒数第二首和最后一首各自然完成两遍，继续观察回到第一首。
- **期望：** 每首恰好两遍后换曲；最后一首之后回到第一首并继续；每次自动换曲都创建该曲的新任务，把已完成累计和模式 session 清零。下一首从有效起点开始时，用户可见“当前遍数”为 1，且不继承上一首的数字。
- **证据：** 倒数第二→最后→第一首的连续录屏和每次 QueueEnded/ActiveTrackChanged 日志。

### P06 快捷遍数

- **前置：** 普通模式，播放模式固定为“单曲循环”，进入“我的 → 每首重复遍数”。
- **步骤：** 依次选择 1、108、1,000、10,000；每次返回播放页核对显示；关闭并重开 App 核对最后值。
- **期望：** 四个快捷值都可选中并持久化；1 时播放页只显示当前遍数、不显示每首重复遍数，其他三个值同时显示当前/总遍数且使用千分位。设置值不因页面切换或重启改变。
- **证据：** 四个选中状态、播放页显示和重启后的截图。

### P07 自定义大数和非法输入

- **前置：** 普通模式，打开自定义遍数输入。
- **步骤：** 分别提交 `5,000,000`、空值、`0`、超过 `Number.MAX_SAFE_INTEGER` 的数字；再粘贴 `-5` 和 `1.5`，逐项记录输入框实际文本与保存值。
- **期望：** 5,000,000 保存、以千分位完整显示并在重启后保留；空值、0、超安全整数被拒绝。当前实现会静默删除非数字，所以 `-5` 变为 `5`、`1.5` 变为 `15`；应如实记录，不能误写成“负数/小数被报错拒绝”。
- **证据：** 每种输入提交前后截图、错误弹窗、重启后值；若产品期望与当前转换不符，关联问题编号。

### P08 手动重选当前曲

- **前置：** 普通模式、同步关闭、N>1；任一曲目已自然完成至少 2 遍，当前遍数可见。
- **步骤：** 进入列表，手动点击当前正在播放的同一首曲目。
- **期望：** 视为明确的新播放任务；已完成累计和模式 session 清零，不保留旧任务的 2 遍。重选后从有效起点播放，因此用户可见“当前遍数”为 1；这个 1 表示正在进行的新任务第 1 遍，不代表已经完成 1 遍。
- **证据：** 重选前后录屏、任务/track generation/计数日志。

### P09 主动关闭/意外退出后的续数

- **前置：** 当前任务至少完成 2 遍，下一遍尚未完成；分别记录已完成累计、`cycle_eligible`、用户可见当前遍数和播放/暂停意图。分别准备主动关闭和可复现的系统终止场景。
- **步骤：** 主动从最近任务关闭后重开；另在不清数据、不 force-stop 的系统回收/崩溃场景后重开。
- **期望：** 同一任务恢复原有已完成累计，不把退出时尚未完成的一遍提前计入，也不重复计数。用户可见“当前遍数”仍按“已完成累计 + 当前周期资格”计算：例如已完成 2 遍且第 3 遍已有资格时，应继续表达正在进行第 3 遍，不能要求页面直接显示内部累计值 2。曲目、资格和用户播放意图按接管/冷重建路径恢复并分别记录；手动重选曲目不属于本用例，应按 P08 清零。
- **证据：** 两类退出各自的退出前/重开后画面、终止方式、系统/App 日志。无法可靠制造系统回收时标 BLOCKED，不得用 force-stop 冒充。

### P10 高频并发操作

- **前置：** 普通模式；准备一首正在播放的曲目并开启诊断采集。
- **步骤：** 在 30 秒内快速交替点击播放/暂停、上一首、下一首、播放模式和同步开关；至少重复 3 轮，最后停止操作等待命令队列收敛。
- **期望：** 不崩溃、不假死、不出现两首重叠；最终曲目/模式/同步/播放状态与最后一次有效输入一致；没有错曲、越界、重复计数或过期事件覆盖新状态。
- **证据：** 全程录屏、时间戳、诊断中的 command queue/generation/stale event 记录；每轮最终状态截图。

## 3. S：同步模式

### S01 从周期中间加入

- **前置：** 设备启用自动时间并记录时区；无该曲累计的新任务；选择一个当前墙钟对齐位置大于 1.5 秒的时刻。
- **步骤：** 开启同步并播放，记录对齐后的起点；让当前尾段结束，再完整观察下一周期。
- **期望：** 首次定位到墙钟对应位置；从中段加入的尾段不计数，新任务显示 0。下一遍若在 0～1.5 秒内取得资格并完整结束，才增加到 1；已有同任务累计时只保留旧累计，不新增尾段计数。
- **证据：** 自动时间/时区截图、起点、首个和第二个 QueueEnded、`seekWithReason` eligible 日志。

### S02 自然换遍

- **前置：** 同步开启、自动时间开启；选择 A04，N 大于 1，确保当前周期从 0～1.5 秒内开始。
- **步骤：** 自然播放到 QueueEnded，持续记录结束回调、重新对齐目标和下一次声音起点；至少完成 3 个周期。
- **期望：** 每次有效周期恰好计 1；结束后按当时墙钟重新对齐，不机械假设 seek 到 0；若目标落在 0～1.5 秒则取得下一遍资格，界面和声音不中断到错误曲目。
- **证据：** 连续录音/录屏、每个 QueueEnded position、native position/duration、sync seek 目标和 eligible 状态。

### S03 暂停后恢复

- **前置：** 同步开启，当前遍已有资格；准备秒表。
- **步骤：** 分别暂停约 1.0 秒、恰好约 1.5 秒和明显大于 1.5 秒后恢复；每种情况让该周期走到结束。因人工计时有误差，记录实际诊断时间而非只写目标值。
- **期望：** 恢复时重新按墙钟对齐；短暂停仅在原资格有效且循环位移不超过 1.5 秒时可保留资格，长暂停/时钟回拨不能把不连续尾段误计完整遍；若恢复目标本身落在 0～1.5 秒，可重新取得资格。
- **证据：** 暂停/恢复时间戳、恢复前后 position、对齐目标、paused 秒数、eligible 和最终计数。

### S04 App/远程 seek 锁定

- **前置：** 同步开启；分别准备 App 进度条、iOS 控制中心/锁屏或 Android 通知/锁屏入口。
- **步骤：** 尝试从 App 和每个系统入口拖到任意位置；返回 App 观察实际进度。
- **期望：** App 不允许任意 seek；系统若仍发出 RemoteSeek，播放器纠正到当前墙钟对齐位置，而不是接受请求位置；不因此授予错误计数资格。
- **证据：** App 与系统入口录屏、RemoteSeek 请求值、纠正目标和 eligible 日志。系统未显示 seek 控件也要截图记录。

### S05 两台同型号设备

- **前置：** 两台同型号/同系统设备，自动时间和相同时区；同一候选 build、同一曲目、同步开启、音量可辨识。
- **步骤：** 尽量同时开始 A05，记录启动后、5 分钟、10 分钟及每个周期边界；中途不手动 seek。
- **期望：** 两台都按各自墙钟对齐并保持可接受的听感同步；无逐周期累积漂移、漏计或一台提前停止。项目尚未定义毫秒级容差，必须记录实测偏差，不能只写“听起来同步”。
- **证据：** 同画面/同录音源视频、设备时钟差、各自诊断文件和测得偏差。

### S06 iOS + Android 跨平台

- **前置：** iOS/Android 各一台真机，自动时间、相同时区和候选 build；同步开启。
- **步骤：** 依次用 A05、A04 和一首长曲同时播放；每首记录启动、至少 3 个周期边界或长曲 10 分钟节点。
- **期望：** 两端对齐算法一致；无平台特有的吞首音、提前结束、累积漂移或计数差异。出现听感差异时保留两端原始日志，不先归因编码或 RNTP。
- **证据：** 跨设备同录视频、每首起点/边界偏差、两端 QueueEnded/seek 日志。

### S07 时钟/时区异常

- **前置：** 一台测试设备；记录正确时区和自动时间状态。只在非日常使用的测试设备上修改时间。
- **步骤：** 关闭自动时间，制造可控时钟或时区差异并播放；再恢复正确时区和自动时间，重新触发同步对齐。
- **期望：** 时钟/时区不一致时允许出现不同步，但 App 不崩溃、不产生非法 position；恢复正确设置后能重新对齐。系统时钟回拨期间不能错误保留连续播放资格。
- **证据：** 修改前后系统时间/时区、对齐目标、eligible/paused 日志和恢复录屏。

### S08 A05 21 遍专项

- **前置：** 真机、候选 release build、同步开启；单曲循环或足以完成 21 遍的设置；设备接电并关闭会主动终止测试的省电限制。
- **步骤：** A05 不 seek 连续自然完成 21 遍；逐遍记录 QueueEnded、event/native position、duration、seek 目标、首个可听声音和计数。
- **期望：** 21 次自然边界不自动停止、不重计/漏计；重新编码后的 A05 不出现可复现的严重吞首音；任何偏差都能关联到具体遍次和日志，而不是只给总体听感。
- **证据：** 21 行节点表、连续录音/录屏、完整诊断和候选 A05 文件 SHA-256。

### S09 其余 20 首

- **前置：** 同步开启；建立 20 首非 A05 的清单。
- **步骤：** 每首至少从有效起点自然完成一个同步周期，记录结束和下一周期起点；长曲可安排过夜，但不得用 seek 缩短。
- **期望：** 每首能解码、自然触发有效 QueueEnded、计数一次并重新对齐；A05 的修复没有掩盖普遍换遍问题。
- **证据：** 20 首逐项 PASS/FAIL 表、每首关键日志；失败曲目保留单独录音和文件哈希。

## 4. L：生命周期、系统控制和硬件

L01～L07 的最终结论必须来自真机。Simulator/Emulator 只能预检，不能标记这些用例 PASS。

### L01 锁屏 30 分钟

- **前置：** 真机、候选 release build；普通/同步/关怀三种能力组合至少分别检查一次。
- **步骤：** 开始播放后锁屏 30 分钟；在开始、15 分钟、30 分钟检查声音、曲目信息和可用按钮。
- **期望：** 音频持续、计数/换曲正确；锁屏元数据对应当前曲；只出现该模式允许的能力。系统空间不足导致按钮折叠时记录实际布局，不将按钮个数硬编码为缺陷。
- **证据：** 三个时间节点、锁屏截图/视频、诊断和系统媒体状态。

### L02 Android 后台/划掉 UI

- **前置：** Android 真机，播放中且通知可见；记录当前曲目、遍数和播放意图。
- **步骤：** Home 到后台，随后从最近任务划掉 UI；继续观察声音/通知，再从图标重开 App。
- **期望：** 按配置继续播放；重开后接管原生队列，曲目、索引、模式、累计遍数和播放意图一致，不重建成错误曲目或清零任务。
- **证据：** 划掉前后录屏、通知、进程/Service 状态、重开画面和 ActiveTrackChanged 日志。

### L03 Android 厂商省电

- **前置：** 至少一台有严格后台策略的厂商真机；记录系统省电模式、App 电池权限和是否在白名单。
- **步骤：** 在默认策略下后台播放至少 2 小时；再按厂商最严格策略重复；如产品提供白名单引导，再按引导重复。
- **期望：** 如未被系统终止，持续播放和计数正确；如被终止，准确记录系统限制、发生时间和恢复行为，不假称所有厂商都能保活。白名单不得掩盖默认策略结果。
- **证据：** 电池设置截图、开始/中间/结束节点、系统终止原因、诊断和恢复结果。

### L04 iOS 后台 30 分钟

- **前置：** iPhone/iPad 真机候选 build；记录当前状态。
- **步骤：** Home 到后台持续播放 30 分钟，期间通过控制中心/锁屏观察；返回 App。
- **期望：** 后台音频持续、系统元数据与控制能力正确；返回后 UI 与原生曲目、位置、状态和累计数一致。
- **证据：** 开始/15/30 分钟节点、控制中心/锁屏和返回 App 录屏、诊断。

### L05 来电/系统音频中断

- **前置：** 真机，分别在同步关闭/开启时播放；可由另一部电话发起来电或使用平台认可的真实中断源。
- **步骤：** 播放中触发来电/系统中断，分别测试接听后结束、拒接、短暂中断；观察暂停和恢复。
- **期望：** 遵从平台音频中断语义；只有原本期望播放时才恢复，不意外自启。非同步的临时 pause/resume 若未发生 seek，应保留原计数资格；同步恢复会重新对齐，只有发生不连续跳转或连续性条件不满足时才让当前尾段失去资格。永久中断停止并取消当前周期资格。
- **证据：** 中断类型/时长、前后状态、RemoteDuck/PlaybackState、eligible 和最终计数。

### L06 其他 App 抢音频焦点

- **前置：** 真机，准备一个会短暂 duck/pause 和一个会长期占用音频的 App。
- **步骤：** 播放中分别触发短暂通知/导航和另一个媒体播放；停止外部音频后返回。
- **期望：** 暂停/duck/恢复符合平台；用户已主动暂停时不被外部事件重新启动；同步恢复重新对齐且资格正确。
- **证据：** 外部事件来源、前后声音/状态视频、RemoteDuck/PlaybackState 日志。

### L07 有线/蓝牙和远程控制

- **前置：** 至少一种有线耳机和一种蓝牙耳机/音箱；当前模式的远程能力已记录。
- **步骤：** 播放中断开/重连设备；使用硬件播放/暂停、上一首、下一首；在同步和关怀模式下复测受限能力。
- **期望：** 路由变化不造成双播或意外自启；远程命令执行一次且最终曲目正确；模式不允许的能力不被错误执行；残缺周期不误计。
- **证据：** 设备型号/协议、操作录屏、Remote 事件、路由/PlaybackState 和计数日志。

### L08 Service/进程重建

- **前置：** Android 播放中并记录队列/任务；另准备 iOS 主动终止后的持久化检查。明确记录使用的终止方法。
- **步骤：** 在系统内存压力或测试工具允许的非 force-stop 场景制造进程/Activity 重建；重开 UI。另单独执行 force-stop，只验证“强制停止后用户再次打开”的行为，不把它当后台恢复。
- **期望：** 可恢复场景中曲目索引、播放模式、累计遍数和 `expected_playing` 与原生状态一致；不把冷启动 Loading 误判为应自动播放。force-stop 与普通回收结果分开记录。
- **证据：** 终止命令/系统条件、前后 PID/Service、原生队列、App 诊断和重开状态。

### L09 诊断导出

- **前置：** 先制造可识别的播放/模式日志；进入“我的 → 诊断信息”。
- **步骤：** 导出 `.txt` 并完成一次系统分享；再导出并取消分享；在可控环境测试分享目标不可用或导出失败。
- **期望：** 文件为 UTF-8 文本，含版本、平台、时间和设备当前保留的全部日志，不受页面最近 30 条预览限制；logger 最多保留 1,000 条、单条最多 2,000 字符。完成/取消/失败不导致崩溃或假报成功。
- **证据：** 脱敏后的文件哈希/受控链接、首尾内容、分享完成/取消/失败画面。

### L10 连续运行

- **前置：** 候选 release build、真机接电；关闭测试无关的系统自动更新，记录电池/温度和网络状态。
- **步骤：** 完成 S08 的 A05 21 遍；另选长曲和列表连续运行至少 2 小时；每 30 分钟记录节点，不进行人工 seek。
- **期望：** 不崩溃、不自动停止、不重复/漏计、不错误换曲；内存、温度和日志无持续恶化迹象。外部系统终止必须记录原因，不能简单归为 App 自动停止。
- **证据：** 开始/每 30 分钟/结束状态、连续诊断、系统资源/终止信息和问题编号。

## 5. U：布局、可用性和无障碍

布局比例使用当前**窗口内容区域的高/宽**，不是设备宣传分辨率；分屏后必须重新按窗口测量。

### U01 竖屏（高/宽 > 1）

- **前置：** iPhone/Android 手机竖屏，普通模式；N>1 让两组遍数都可见。
- **步骤：** 浏览播放、列表、“我的”；播放中操作五按钮、进度和遍数。
- **期望：** 使用竖屏布局；五按钮同一行且垂直居中；当前遍数在进度条上、总重复遍数在下，时间可读且不与安全区冲突。
- **证据：** 带设备/窗口尺寸的三页截图和关键操作录屏。

### U02 方屏边界（0.75 ≤ 高/宽 ≤ 1）

- **前置：** 用 iPad 分屏/可调 Emulator 分别制造恰好 1、恰好 0.75 及区间内窗口。
- **步骤：** 在三个尺寸之间切换，保持播放；检查左控制轨、中心唱片、右进度轨。
- **期望：** 两个等号边界都归入方屏；三栏完整且无临界抖动，左右轨等高，播放按钮中心、唱片圆心和遍数组中心位于同一水平轴；尺寸变化不触发 seek/reset。
- **证据：** 实际窗口宽高、三个边界截图和不中断录屏。

### U03 横屏（高/宽 < 0.75）

- **前置：** 手机或平板宽横屏，实际比例小于 0.75。
- **步骤：** 播放并操作左侧控制轨；观察中心唱片和右侧竖进度/遍数。
- **期望：** 使用横屏三栏；左/右轨等高，五个控制垂直排列且可达，右侧显示完整时间/遍数，中心元素不被压缩或遮挡。
- **证据：** 窗口尺寸、全屏截图和五控件操作录屏。

### U04 旋转/分屏连续性

- **前置：** 正在播放且当前任务已有累计遍数；同步模式分别开/关测试。
- **步骤：** 竖→横→竖旋转；iPad 进入/退出分屏并拖动分隔条跨过 1 和 0.75 边界。
- **期望：** 曲目、位置、播放状态、累计、session 和同步资格连续；只重排 UI，不 reset、不额外 seek、不重复创建队列。
- **证据：** 全程录屏、每次窗口尺寸、旋转期间播放器命令/QueueEnded 日志。

### U05 安全区

- **前置：** 至少一台刘海/灵动岛 iPhone、一台有手势导航/圆角的 Android 和 iPad。
- **步骤：** 三类布局下检查顶部、底部、横屏左右边缘并操作最靠边控件。
- **期望：** 标题、Tab、按钮、进度和文字不被系统栏、Home indicator、摄像头区域或圆角遮挡；触控区域完整。
- **证据：** 每设备竖/横截图和边缘控件点击录屏。

### U06 大数字

- **前置：** 自定义 5,000,000，并制造较大的当前累计或使用受控测试数据；普通模式。
- **步骤：** 在竖/方/横、小屏、分屏和大字体下检查；用读屏聚焦两个数字。
- **期望：** 可见值有稳定千分位，完整显示或合理缩放，不与时间/进度重叠；读屏分别表达当前遍数和每首重复遍数的完整含义，而非只读裸数字。
- **证据：** 各布局截图、VoiceOver/TalkBack 实际朗读录屏。

### U07 关怀模式

- **前置：** 普通模式中记录当前曲、状态和设置。
- **步骤：** 开启关怀模式，播放/暂停并旋转；进入“我的”恢复普通模式。
- **期望：** 播放键明显放大，只保留设计允许的核心操作，列表 Tab/易误触功能隐藏；状态不丢失，返回普通模式路径始终可达。
- **证据：** 开关前后竖/宽布局、返回路径和播放操作录屏。

### U08 字体/显示缩放

- **前置：** 每个平台准备默认、约 135%、200% 字体/显示大小；记录具体系统档位。
- **步骤：** 每档浏览三页、四种模式文案、自定义输入/错误、诊断展开；横竖屏各一次。
- **期望：** 核心内容和操作不丢失、不重叠；可滚动内容可达；文字不会被缩到不可读。出现固定字号不跟随系统时记实际缺口，不因布局“没坏”就 PASS 动态字体。
- **证据：** 每档关键页截图、滚动到末尾和弹窗录屏。

### U09 VoiceOver/TalkBack

- **前置：** iOS/Android 真机开启对应读屏；普通模式。当前项目只能声称局部支持，验收缺口见 [ACCESSIBILITY.md](ACCESSIBILITY.md)。
- **步骤：** 不看屏幕完成选曲、播放/暂停、上下首、四模式、同步、遍数设置、关怀模式切换和诊断导出；旋转后继续。
- **期望：** 焦点顺序、role、label、state 和动态反馈足以完成主路径；装饰元素不制造噪声，进度刷新不持续抢焦点。任一关键路径不可完成即 FAIL/PARTIAL，不以 Jest props 代替。
- **证据：** 带读屏声音的完整录屏、设备/读屏版本、缺失语义清单和问题编号。

### U10 Reduce Motion/对比度

- **前置：** 分别开启 Reduce Motion/移除动画、增加对比度、反转/颜色滤镜等平台能力。
- **步骤：** 播放/暂停并检查唱片、光晕、焦点、选中态和所有正文；与系统设置关闭时对比。
- **期望：** 运动效果遵循系统设置，状态不只依靠颜色；正文/大字/重要图标达到项目约定的对比标准。当前实现尚未完整适配 Reduce Motion/对比度，发现缺口应如实 FAIL/PARTIAL，不能更改预期来迁就实现。
- **证据：** 系统设置和前后录屏、颜色测量值/工具报告、问题编号。

## 6. 建议执行顺序

1. 冻结 commit、构建并计算制品哈希。
2. 执行 `docs/TESTING.md` 的自动化门槛和原生 smoke。
3. Simulator/Emulator 预检 P、U 和 L08/L09 的可执行部分。
4. 在 iOS/Android 真机执行 P01～P10，再执行 S01～S09。
5. 执行 L01～L10 和 U01～U10；长时与多设备测试可并行，但必须属于同一候选制品。
6. 汇总 FAIL/BLOCKED/NOT RUN、已知风险和批准人；任何修复都会产生新 commit/build，并应新建一轮记录。
7. 通过 [双端发布手册](RELEASE.md) 完成发布；发布后从真实渠道安装并再次执行规定的冒烟检查。

本手册描述“怎么测”，`DEVICE_TEST_MATRIX.md` 描述“哪些设备/场景必须覆盖”，`test-runs/` 描述“某个版本实际测了什么”。三者不可相互替代。
