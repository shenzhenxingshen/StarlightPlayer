# 版本测试执行记录

本目录保存“某个不可变候选制品实际执行了哪些测试”的 Markdown 索引。测试方法见 [`../TESTING.md`](../TESTING.md)，步骤见 [`../QA_PLAYBOOK.md`](../QA_PLAYBOOK.md)，目标设备覆盖见 [`../DEVICE_TEST_MATRIX.md`](../DEVICE_TEST_MATRIX.md)。

## 1. 为什么单独留档

`DEVICE_TEST_MATRIX.md` 是长期要求和当前证据摘要，不应被当作每次发布的原始记录。每个候选 build 都需要一个独立文件，将以下对象绑定在一起：

- Git commit；
- 营销版本和平台构建号；
- 实际安装制品及 SHA-256；
- 设备、OS、安装/升级路径和环境；
- 自动化结果、P/S/L/U 每项状态；
- 外部证据、问题、例外和发布批准。

没有这层绑定，“以前测过”无法证明当前二进制可发布。

## 2. 新建记录

从 [`TEMPLATE.md`](TEMPLATE.md) 复制一个新文件，推荐命名：

```text
YYYY-MM-DD-v<version>-b<build>-<platform>-<short-commit>-<run>.md
```

例如：

```text
2026-10-16-v1.0.0-b4-ios-0698f62-r01.md
2026-10-16-v1.0-b3-android-0698f62-r01.md
```

一个记录只对应一个平台候选制品；同一制品在多台设备上的结果可以写在同一记录中。修复后 commit/build/哈希任一变化，都新建记录，不覆盖旧文件。`run` 递增用于同一制品的独立复测。

## 3. 不可变规则

记录在状态为 `DRAFT` 时可以补充；一旦用于发布决定并标为 `FINAL`：

1. 不改写原结果、时间、证据或批准结论；
2. 发现笔误时在末尾追加带日期/作者的“更正说明”，保留原值和更正值；
3. 功能复测新建 `r02` 等新文件，并用 `SUPERSEDES` 指向旧记录；
4. 新 build 必须新建记录，即使源码看似只有版本号变化；
5. 旧记录的外部证据不得无声替换；迁移存储时同时保留旧/新 URI、哈希和迁移日期。

Git 历史提供修改轨迹，但不能代替上述记录纪律。

## 4. 外部证据策略

仓库只保存小型、脱敏的执行摘要。以下原始材料默认放到有访问控制、版本保留和备份的外部制品/测试存储：

- `.xcresult`、完整 xcodebuild/Gradle/Metro/logcat/sysdiagnose/bugreport；
- 长录屏、音频、多设备同步视频、全分辨率截图；
- App 诊断原文、崩溃文件和可能含设备标识/账号/通知的日志；
- APK/AAB/IPA/Archive 和签名详情。

每项外部证据在记录中填写：

- 唯一证据 ID，例如 `EV-S08-001`；
- 对应测试 ID 和采集时间；
- 受控 URI（不要写临时本机绝对路径）；
- 文件 SHA-256、大小和格式；
- 是否已审阅/脱敏、访问范围和保留到期日；
- 采集设备/build；如果做过转码/压缩，同时记录原件和衍生件哈希。

链接失效前迁移到长期存储并追加迁移说明。只提供截图但无法关联 build/时间的材料最多支持 PARTIAL。用户发来的诊断不可直接放进公开仓库；应先取得适当授权并脱敏。

## 5. 有效 PASS 的最低条件

一个用例标为 PASS 必须同时具备：

- 执行的是记录中的精确候选制品；
- 前置和步骤完整，参数/设备组合符合 `QA_PLAYBOOK.md`；
- 实际结果满足全部预期，而不只是“没有崩溃”；
- 有测试者、开始/结束时间和至少一个可核验的证据 ID；
- 没有未解释的失败；基础设施问题应为 BLOCKED，未执行应为 NOT RUN。

模拟器结果不能让真机 L01～L07 变成 PASS，Jest 覆盖率不能让原生行为变成 PASS，旧版本用户反馈也不能直接成为当前候选 PASS。

## 6. 仓库当前状态

本目录建立时只有流程和模板，没有可追溯的历史版本执行文件。`TESTING.md` 与 `DEVICE_TEST_MATRIX.md` 中的 2026-10-16 基线属于已核对摘要，不应事后伪造为完整 `FINAL` 记录。下一次候选应从模板开始正式留档。
