# A05 桌面音频引擎第一阶段验证

日期：2026-11-11（Asia/Shanghai）  
分支：`codex/v1.1-scheduled-tasks`  
移动端冻结基线：`2ef6bc9356a07d320a0ccd0542ed65fbb7c4d22f`

## 1. 目标

使用当前移动端正式候选中的同一份 A05，对 miniaudio 与 libmpv 分别验证：

1. 连续运行 21 个完整周期；
2. 每周期是否产生且只产生一次开始/结束事件；
3. 周期是否发生累计漂移；
4. 原生连续队列/回卷是否插入或丢失 PCM 帧；
5. 这些引擎是否值得进入 Tauri 桌面原型下一阶段。

本阶段不修改移动端播放逻辑，也不以桌面结果替代 iOS/Android 真机验证。

## 3. 实时21周期结果

| 指标                     |                  miniaudio |                       libmpv |
| ------------------------ | -------------------------: | ---------------------------: |
| 开始/结束事件            |                    21 / 21 |                      21 / 21 |
| 播放/解码错误            |                          0 |                            0 |
| 周期开始间隔均值         |              70,383.539 ms |                70,375.262 ms |
| 周期开始间隔最小/最大    | 70,369.592 / 70,389.688 ms |   70,201.915 / 70,389.440 ms |
| 去掉首次切换后的间隔均值 |              70,384.273 ms |                70,384.386 ms |
| 去掉首次切换后的标准差   |                   4.963 ms |                     4.576 ms |
| 第21遍开始事件累计偏移   |                 -26.725 ms |                  -192.261 ms |
| 第21遍结束事件累计偏移   |                 -22.434 ms |                  -199.428 ms |
| 结束到下一开始事件间隔   |             同一回调，0 ms | 0.122–0.819 ms，均值0.437 ms |
| 精确帧周期               |                    20 / 20 |                由离线PCM验证 |

解释：

- miniaudio 在同一设备回调内读完当前解码器、seek到第0帧并继续填满剩余输出缓冲；20个换遍边界的输出帧索引全部精确相差 `3,103,973`。
- libmpv 的首次队列切换事件相对业务时长提前约183 ms，后续19个间隔均值与文件时长只差约0.489 ms。最终约192 ms不是逐遍累积，而是首次建立gapless设备缓冲后形成的固定状态提前量。
- `END_FILE`/`START_FILE`是播放器状态事件，不等于扬声器已经播到相同物理时刻。不能把libmpv约190 ms的事件提前量直接解释为吞音。

## 4. PCM样本级结果

两个引擎均生成21周期、44.1 kHz、s16、双声道PCM流，并与源A05逐周期比较：

| 指标              |  miniaudio |     libmpv |
| ----------------- | ---------: | ---------: |
| 实际总帧数        | 65,183,433 | 65,183,433 |
| 与理论帧数差      |          0 |          0 |
| 完整周期          |    21 / 21 |    21 / 21 |
| 与源PCM逐字节一致 |    21 / 21 |    21 / 21 |
| 插入或丢失帧      |          0 |          0 |

这证明在当前A05、本地文件、固定输出格式与原生连续队列条件下，两种引擎都不会在解码/队列层吞掉开头样本。libmpv使用了`gapless-audio=yes`、44.1 kHz、s16、stereo固定参数。

## 5. 结论

两种方案都通过第一阶段，均可进入下一阶段；当前没有证据因“吞音”淘汰libmpv。

- **libmpv更适合快速形成Tauri桌面原型**：原生播放列表、格式与设备兼容、事件API较完整；A05 21项队列PCM完全连续。
- **miniaudio更适合追求最小依赖和帧级权威控制的自研引擎**：边界行为最清楚、许可证宽松，但队列、媒体状态、设备恢复和平台集成都要自行完成。
- 如果优先开发效率，第二阶段建议先走`Tauri + libmpv`，同时保留miniaudio探针作为性能/行为基线。

## 6. 尚未证明的事项

1. 本次没有物理回环录音。macOS输出设备运行在48 kHz，而源文件为44.1 kHz；CoreAudio最终重采样、硬件缓冲与扬声器声学输出仍需BlackHole或外部录音接口验证。
2. 尚未在Windows WASAPI、Linux PipeWire/PulseAudio及macOS Intel上复测。
3. 尚未验证同步模式在周期边界执行非零seek时的声音响应；本次重点是连续原生队列。
4. 尚未验证睡眠唤醒、输出设备切换、蓝牙、独占模式、长达数小时运行和定时任务抢占。
5. Homebrew mpv携带GPL/LGPL及大量依赖；正式分发前必须冻结可复现构建并完成许可证、Universal dylib、签名、公证和Linux可移植性审计。

## 7. 下一阶段建议

1. 建立最小Tauri 2桌面壳，只让Rust负责libmpv适配器，继续以共享TypeScript作为业务规则权威。
2. 增加同步seek矩阵：目标位置0、100、250、500、1,500 ms以及曲尾前后边界，各运行21遍。
3. 使用BlackHole回环捕获实际系统输出，测量每个边界的静音长度和第一段非静音样本是否缺失。
4. 分别在Windows、macOS arm64/x86_64、Linux完成相同CSV和PCM契约测试。
5. 在做UI前先验证输出设备切换、睡眠恢复和系统媒体中心适配。
